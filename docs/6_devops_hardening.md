# تحصين بيئة DevOps وسلاسل النشر (DevOps & Infrastructure Hardening)
**المشروع:** نظام إدارة الكهرباء الذكي (SEMS)  
**المجال:** أمان الحاويات، التكامل المستمر، والبنية التحتية  

---

## 1. مراجعة وتأمين إعدادات Docker (Docker Configuration Security)

### أ. تشغيل الحاويات بمستخدم غير جذر (Non-Root User)
في ملفات `Dockerfile` الحالية:
- الباكيند والذكاء الاصطناعي يعملان بصلاحيات المستخدم الافتراضي وهو الـ `root`.
- **الخطر:** في حال نجاح مهاجم في اختراق الحاوية وتنفيذ أوامر RCE (Remote Code Execution)، سيمتلك صلاحيات كاملة على الخادم المضيف.
- **التوصية:** تعديل ملفات `Dockerfile` لإنشاء مستخدم محدد للتشغيل ذي صلاحيات محدودة.
  * *مثال للباكيند (Dockerfile):*
    ```dockerfile
    # إنشاء مستخدم node وتخصيص المجلد له
    USER node
    ```

### ب. إغلاق المنافذ غير الضرورية (Port Hardening)
في ملف `docker-compose.yml`:
- يتم عمل خرائط (Mapping) للمنافذ التالية للخارج: `5432` لقاعدة البيانات، `8000` للذكاء الاصطناعي، `9090` لبروميثيوس.
- **التوصية:** في بيئة الإنتاج، يجب إزالة هذه الخرائط بالكامل وجعل الحاويات تتواصل داخلياً عبر شبكة Docker الافتراضية (Docker Network). المنفذ الوحيد الذي يجب فتحة للخارج هو منفذ البوابة (Nginx Proxy/Gateway) على المنفذ `80` أو `443` ومنفذ لوحة تحكم الإدارة `3000` (إذا لم تكن خلف البوابة).

## 2. جاهزية Kubernetes (Kubernetes Readiness)
لنقل النظام من Docker Compose البسيط إلى بيئة إنتاج ذات موثوقية عالية وقابلية توسع تلقائية باستخدام Kubernetes (K8s):

### المتطلبات الأساسية للنشر في K8s:
1. **تجهيز ملفات البيانات التعريفية (Deployment Manifests):** إنشاء ملفات `deployment.yaml` و `service.yaml` لكل من الخدمات الثلاث (Backend, Dashboard, AI Service).
2. **إعداد فحوصات الصحة (Probes):**
   - **Liveness Probe:** للتحقق مما إذا كانت الحاوية تعمل (مثلاً استدعاء `/api/health` للباكيند).
   - **Readiness Probe:** للتحقق مما إذا كانت الخدمة جاهزة لاستقبال الطلبات (بعد اكتمال اتصال قاعدة البيانات).
3. **إدارة الأسرار (Kubernetes Secrets):** عدم إدراج كلمات مرور قاعدة البيانات أو مفاتيح التشفير كمتغيرات بيئة واضحة، بل حفظها في `K8s Secret` وحقنها وقت التشغيل.

## 3. أمان سلاسل التكامل والنشر (CI/CD & Secret Management)

### أ. تحصين GitHub Actions:
في الملف `.github/workflows/deploy.yml`:
- يجب التأكد من عدم كتابة أي كلمات مرور صلبة.
- استخدام ميزة **GitHub Actions Secrets** لحفظ بيانات الوصول للسيرفر أو مفاتيح SSH بشكل آمن بالكامل.

### ب. مقترحات إدارة الأسرار (Secret Management):
للمؤسسات الكبيرة، يوصى بالانتقال من استخدام ملفات `.env` المحلية إلى نظام متكامل لإدارة المفاتيح والأسرار مثل **HashiCorp Vault** أو خدمات إدارة الأسرار السحابية (AWS Secrets Manager / Google Cloud Secret Manager) لضمان تشفير وتدوير المفاتيح (Key Rotation) بشكل دوري وتلقائي.
